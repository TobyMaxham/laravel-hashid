# Upgrade laravel-hashid from 1.x to 2.0

Agent instructions. Work through the steps in order. Steps marked with **ASK** need a decision of the user.
Background for every step: [UPGRADING.md](https://github.com/TobyMaxham/laravel-hashid/blob/main/UPGRADING.md#from-1x-to-20).

## Step 1: Check the requirements

2.0 requires PHP 8.3+, Laravel 12 or 13 and `hashids/hashids` 5.

- Check `php -v`, the `php` constraint and `laravel/framework` in `composer.json`.
- If the app runs Laravel 10 or 11 or PHP < 8.3: **stop** and tell the user to upgrade Laravel / PHP first. Do not upgrade Laravel as part of this task.
- If the app requires `hashids/hashids` directly, it must allow `^5.0`. Version 5 creates the same hashes as 4.

## Step 2: Find all usages

Search the app (not `vendor/`) and keep the results for the next steps:

```sh
grep -rn "TobyMaxham\\\\HashId" app/ routes/ config/ database/ tests/ resources/ --include="*.php" 2>/dev/null
grep -rnE "use Hasher;|IdHasher::|IdHasherManager|WrongIdException|safeHashID|hashID\(\)|resolveRouteBinding|HasUuids|HasUlids" app/ routes/ tests/ --include="*.php" 2>/dev/null
grep -rn "HASH_" .env.example config/ 2>/dev/null
```

Note: models with the `Hasher` trait, custom code that calls `IdHasher::decodeId()` / `encodeId()`, overrides of `resolveRouteBinding()` / `resolveRouteBindingQuery()`, usages of `safeHashID()` and `WrongIdException`.

## Step 3: ASK how to handle the old hashes

**All hashes change in 2.0**, because every model gets its own hashes (`per_model`). Links in emails, bookmarks, QR codes, and ids stored in other systems or in the database (e.g. in JSON columns or logs) stop working.

Look for hints first, so you can give the user a good recommendation:
- Hashes in mails, notifications, signed URLs, exports or API responses to other systems.
- Hashes stored in the database or cache.

Then ask the user to choose one option (recommend **a** if anything outside the app may have stored a hash):

| Option | `.env`                     | Effect                                                                                  |
|--------|----------------------------|-----------------------------------------------------------------------------------------|
| **a**  | `HASH_ACCEPT_LEGACY=true`  | New hashes per model, old 1.x hashes still work. Remove later. Requires unchanged prefix. |
| **b**  | `HASH_PER_MODEL=false`     | Keep the 1.x hashes forever. Same hashes as before for all models.                      |
| **c**  | nothing                    | Hard switch, old hashes return 404.                                                     |

Add the chosen variable to `.env.example` with a short comment and to the report for the user.

If the user chose **a** or **c** (per-model hashes): the model key is the table name. **ASK** if a table may be renamed later. If yes, set a fixed key on the model, e.g. `public const HASH_ID_KEY = 'products';` (the current table name, so the hashes do not change now).

## Step 4: Update the package

```sh
composer require tobymaxham/laravel-hashid:^2.0 -W
```

If composer fails because of other packages, report the conflict to the user. Do not remove or downgrade other packages without asking.

## Step 5: Check the salt

Run `php artisan about` and look at the "Laravel HashID" section. If it warns about the default salt (`your-salt-string`):
- tell the user to set `HASH_SALT` to a random secret in every environment,
- **but** a new salt changes all hashes. If the app already runs in production with the default salt, **ASK** first. To keep old links working after a new salt, set `HASH_PREVIOUS_SALTS=your-salt-string`.

Never print the salt.

## Step 6: Update a published config

Only if `config/hashids.php` exists in the app:

- Add the missing keys, keep all existing values:

  ```php
  'prefix_mode'          => env('HASH_PREFIX_MODE', 'strict'),
  'previous_salts'       => env('HASH_PREVIOUS_SALTS', ''),
  'per_model'            => env('HASH_PER_MODEL', true),
  'accept_legacy_hashes' => env('HASH_ACCEPT_LEGACY', false),
  ```

- Replace `\TobyMaxham\HashId\Exceptions\WrongIdException::class` with `\TobyMaxham\HashId\Exceptions\InvalidHashIdException::class`, unless the app uses its own exception class.
- If `exception_message` is still `'WrongIdException'`, change it to `'The given hash id is invalid.'`. Check tests that assert the old message first.
- The config is validated now. Check that the prefix (also `HASH_ID_PREFIX` constants and `$hashIdPrefix` of models) only contains `a-z A-Z 0-9 - . _ ~ :`, that `length` is a non-negative integer and that `exception` is an exception class. If not, **ASK**, because a new prefix changes all hashes.

## Step 7: Fix the code

Go through the results of step 2.

**Facade decode / encode of model ids.** `IdHasher::encodeId()` / `decodeId()` use the global salt, not the hashes of a model. If the code decodes a route key or hash of a model, change it (not needed with option **b**):

```php
// before
$id = IdHasher::decodeId($hash);
$product = Product::findOrFail($id);

// after
$product = Product::findByHashIdOrFail($hash);
// or, if only the id is needed
$id = IdHasher::for(Product::class)->decodeId($hash);
```

Only keep `IdHasher::encodeId()` / `decodeId()` for values that are not model keys.

**Route binding overrides.**
- `resolveRouteBinding()` overrides that call `parent::resolveRouteBinding()`: nothing to do.
- `resolveRouteBindingQuery()` overrides: they must call `parent::resolveRouteBindingQuery()`, otherwise the hash is not decoded.
- Code that calls `resolveRouteBinding()` directly and checks for `null` on an invalid hash: it throws `ModelNotFoundException` now. Catch it or use `findByHashId()`.

**UUID / ULID models.** Remove `use Hasher;` (and `implements Hashing` / `HasHashId`) from models that also use `HasUuids` or `HasUlids`. Both define `resolveRouteBindingQuery()` and hashing never worked for these keys.

**`safeHashID()`** returns a `string` now. Wrap calls that use `Stringable` methods: `Str::of($model->safeHashID())->upper()`.

**Exceptions.** `catch (WrongIdException $e)` still works, but the class is deprecated. Replace it with `InvalidHashIdException`.

**Name collisions.** The trait adds `hashIdKey()`, `hashIdPrefix()`, `hashIdManager()`, `decodeHashId()`, `decodeHashIds()`, `findByHashId()`, `findByHashIdOrFail()`, `findManyByHashIds()` and the scopes `whereHashId()`, `orWhereHashId()`, `whereHashIdIn()`, `whereHashIdNot()`, `whereHashIdNotIn()`. The package registers the request macros `hashId()` and `hashIds()`. If the app defines methods or macros with these names, **ASK** whether to rename them.

**Manager.** If the app creates `new IdHasherManager(...)` or extends it: the constructor is now `(?string $prefix = null, ?string $prefixMode = null, ?string $salt = null, ?array $fallbackSalts = null)` and all methods are typed. Prefer resolving it from the container.

**Interface (optional).** Replace `implements Hashing` with `implements HasHashId` on models with the `Hasher` trait.

**Multi-number hashes.** `decodeId()` rejects hashes with several numbers or numbers > `PHP_INT_MAX`. Only relevant if the app created hashes with `Hashids::encode(1, 2)` and decodes them with this package.

## Step 8: Tests

- Tests with hard coded hashes (e.g. `'h:J7dVgYxKPwyQejOMnL'`) fail with per-model hashes. Replace them with `$model->hashID()` or `Model::factory()->create()->getRouteKey()`. Do not change the hash config to make old fixtures pass.
- Tests that expect `null` from `resolveRouteBinding()` for an invalid hash must expect `ModelNotFoundException`.
- Tests that assert the message `'WrongIdException'` must use the new message (if the config was changed).
- Run the test suite and static analysis. Fix failures caused by the upgrade, report others.

## Step 9: Optional improvements

Only suggest these to the user, do not apply them without asking:

- Validation rules `HashId` / `HashIdExists` instead of manual decode in form requests.
- `$request->hashId('product_id', Product::class)` in controllers.
- `SerializesHashIds` to hash ids (and foreign keys) in JSON.
- `php artisan hashid:encode` / `hashid:decode` for debugging.

## Step 10: Report

Use the report format of [SKILL.md](../SKILL.md#3-report). Always include:

- the chosen option for the old hashes and the `.env` values for every environment,
- if `HASH_ACCEPT_LEGACY=true` was set: remind the user to remove it later, once old links are no longer needed,
- places where hashes may be stored outside the app (you cannot check these).
